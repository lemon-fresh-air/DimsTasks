# Модель даних DimsTasks

Компонування груп на екранах «Сьогодні» і «Завтра» описане в [today-groups.md](today-groups.md). Воно є окремою моделлю представлення з локальною датою, групами й зовнішньою послідовністю; поле `groupId` до Task не додається. Кожна дата має окремий запис `day-plan:YYYY-MM-DD` у store `settings`.

DimsTasks зберігає доменні об'єкти в чотирьох окремих object stores IndexedDB: `lists`, `sections`, `projects`, `tasks`. Окремий store `settings` зберігає локальні налаштування інтерфейсу. Екрани й картки є лише представленнями цих записів і не дублюють дані.

## Спільні поля

Кожен запис має стабільний `id`, `entityVersion`, ISO-час `createdAt` і `updatedAt`, а також `customFields` для експериментальних чи користувацьких атрибутів. Нові звичайні поля можна додавати без зміни версії IndexedDB; версію бази потрібно піднімати лише при зміні object stores або індексів.

## Сутності

### List

```js
{ id, entityVersion, title, description, kind, position, customFields, createdAt, updatedAt }
```

`kind`: `inbox | regular`. Системний Інбокс має стабільний id `system-list-inbox` і створюється автоматично.

### Section

```js
{ id, entityVersion, listId, title, description, position, collapsed, customFields, createdAt, updatedAt }
```

Секція завжди належить одному списку. Завдання може посилатися лише на секцію зі свого `listId`. `collapsed` за замовчуванням `false`; згортання приховує завдання лише на екрані списку, не змінюючи їхніх записів. Кількість біля секції показує видимі активні завдання в ній.
У версії 0.15 секції створюються лише у звичайному списку. Їхній порядок визначає `position`, порожні секції залишаються видимими. У списку спершу відображаються завдання з `sectionId: null`, далі секції зі своїми завданнями. Видалення секції атомарно скидає `sectionId` її завдань у `null`, не змінюючи `listId`. Після вибору списку з секціями редактор пропонує одну з них або «Без секції». Перехід до іншого списку спершу скидає `sectionId`, після чого користувач може обрати секцію нового списку.

### Project

```js
{ id, entityVersion, title, goal, description, status, dueDate, dueTime, showCountdown,
  lastListId, defaultListId, addNewTasksFirst, completedAt, position, customFields, createdAt, updatedAt }
```

`status`: `active | completed`. Завершення проєкту підтверджується вручну.
`showCountdown` за замовчуванням `false`; коли значення `true` і задано `dueDate`, інтерфейс обчислює календарну кількість днів від поточної локальної дати, не зберігаючи її в базі.
`lastListId` запам'ятовує останній список, обраний для кроку цього проєкту. Нові кроки створюються в ньому; для старого запису, відсутнього або видаленого списку застосунок використовує Інбокс.
`defaultListId: null` означає автоматичний режим через `lastListId`. Вибраний у налаштуваннях фіксований список має пріоритет для нових кроків, але список окремого завдання можна змінити. Якщо фіксований список видалено, нові кроки потрапляють до Інбоксу.
`addNewTasksFirst` за замовчуванням `false`. Коли значення увімкнене, новий крок стає першим у проєкті та в корені свого списку; коли вимкнене — додається в кінець обох порядків. Явно збережене значення наявного проєкту зберігається.

### Task

```js
{ id, entityVersion, listId, sectionId, projectId, title, description,
  status, completedAt, dueDate, dueTime, position, todayPosition, projectPosition,
  returnedToInboxAt, savedSteps, customFields, createdAt, updatedAt }
```

`listId` обов'язковий; за замовчуванням це Інбокс. `sectionId` і `projectId` можуть бути `null`. `position` задає порядок у списку/секції, `projectPosition` — незалежний порядок кроків проєкту. `todayPosition` зберігається для сумісності зі старими записами й одноразово переноситься до плану поточної дати; нове впорядкування його не змінює. `status`: `active | completed | archived`.

Описи Task і Project зберігаються в наявному полі `description` як Markdown: `**жирний**`, `*курсив*`, марковані й нумеровані списки, `[назва](https://…)`. Підкреслення записується як `<u>текст</u>`. Редактор показує форматований результат; копіювання кладе Markdown у `text/plain` і форматований HTML у `text/html`. Для YouTube-посилань назва відео може завантажуватися через oEmbed; без мережі лишається клікабельне посилання. Нових полів, stores, індексів чи версії бази це не потребує.

`savedSteps` — структурований масив знімків `{ title, description, status, listId, sectionId }` лише для самостійного завдання. Відсутнє поле читається як `[]`; порядок масиву є порядком кроків. При перетворенні проєкту зберігаються лише активні невиконані кроки; виконані й архівні видаляються. Знімки не мають власних ID і не змінюються при видаленні списку чи секції. Старі знімки з виконаним станом відновлюються виконаними. Завдання з непорожнім `savedSteps` не можна приєднати до іншого проєкту як його крок.

Дата зберігається як локальне `YYYY-MM-DD`, час окремо як `HH:mm`; це дозволяє мати дату без часу. Час без дати не зберігається. Завдання з датою без часу прострочується після завершення дня, а з часом — одразу після вказаної локальної хвилини. `completedAt` заповнюється лише після виконання. `returnedToInboxAt` — ISO-час одноразового автоматичного перенесення простроченої активної задачі до Інбоксу; для інших задач `null`. Дедлайн при перенесенні не змінюється.

### Settings

План кожної локальної дати зберігається окремим атомарним записом:

```js
{ id: `day-plan:${date}`, entityVersion, date, groups, items, createdAt, updatedAt }
```

`date` — локальне `YYYY-MM-DD`; `groups` містить `{ id, color, title, collapsed, taskIds }`, а `items` — посилання `{ type: "group" | "task", id }`. Порядок `items` зберігається і без груп та належить тільки даті запису. `title: null` означає стандартну назву за кольором; користувацька назва містить від 1 до 80 символів. Старі групи без `title` читаються як групи зі стандартною назвою. Належність задачі існує тільки в `groups[].taskIds`. Злиття груп залишає ID, назву та місце вибраної групи. План іншої дати ніколи не застосовується. Старий `today-layout` атомарно переноситься до плану своєї дати, а старий порядок `todayPosition` — один раз до плану поточної дати. Нового store, індексу або версії IndexedDB не потрібно.

Перетягування згорнутої групи або незгрупованих задач між групами змінює тільки порядок `items`, не змінюючи `groups[].taskIds` або позиції задач. Масове виконання групи оновлює статус її активних задач; після завершення порожня група зникає під час нормалізації. Скасування протягом 3 секунд відновлює попередні записи задач.

Коли на екрані «Сьогодні» виконують поточний крок проєкту з кольорової групи, наступний активний крок цього проєкту займає його місце в тій самій групі, якщо він теж видимий на цю дату. Запис завдання та плани інших дат не змінюються.

Налаштування вигляду зберігаються записом зі стабільним id `appearance`:

```js
{ id: "appearance", entityVersion, theme, useSystemTheme, createdAt, updatedAt }
```

`theme`: `light | dark` — останній ручний вибір. `useSystemTheme` за замовчуванням `true`; коли він увімкнений, фактична тема береться з `prefers-color-scheme`, а ручний перемикач неактивний. Старі записи без поля також використовують системну тему. Store `settings` додано міграцією версії бази 2→3 без змін або видалення наявних записів.

Типовий список для послідовного створення завдань на екрані «Сьогодні» зберігається окремим записом:

```js
{ id: "task-defaults", entityVersion, todayListId, createdAt, updatedAt }
```

Значення оновлюється лише після успішного створення нового завдання зі «Сьогодні». Скасування та редагування наявних завдань його не змінюють. Якщо вказаного списку більше немає, застосунок використовує Інбокс.

Поведінка прострочених задач зберігається окремим записом:

```js
{ id: "workflow", entityVersion, returnOverdueToInbox, createdAt, updatedAt }
```

`returnOverdueToInbox` за замовчуванням `false`. Коли значення `true`, активні прострочені задачі з інших списків без `returnedToInboxAt` один раз переносяться до кореня Інбоксу стабільним порядком перед його наявними задачами. Вимкнення не скасовує виконаних перенесень.

Стартовий екран нижньої навігації зберігається окремим записом:

```js
{ id: "navigation", entityVersion, startScreen, createdAt, updatedAt }
```

`startScreen`: `today | upcoming | projects | inbox | overview`; за відсутності або некоректного значення застосунок відкриває `inbox` («Нові»).

Назва наступної резервної копії зберігається окремим записом:

```js
{ id: "backup-naming", entityVersion, prefix, nextVersion, createdAt, updatedAt }
```

`prefix` за замовчуванням `Dimstasks`. `nextVersion` починається з `1` і збільшується після кожної успішно підготовленої копії. Експортований JSON містить наступний номер; під час імпорту також читається номер з імені файлу, якщо воно має вигляд `Dimstasks-3---18-Oct-2026.json`. Для наступного експорту береться найбільше значення з локального лічильника, JSON та номера файлу плюс один. Це дозволяє продовжити нумерацію зі старих файлів без `backup-naming`. Дата в імені формується за локальним часом пристрою. Незалежні експорти на двох пристроях до обміну файлами все ще можуть отримати однаковий номер.

## Обчислювані правила

- Поточний крок проєкту — перше активне завдання за `projectPosition`; він не зберігається окремо. На КП активні кроки показуються перед виконаними, а в межах кожної групи зберігається `projectPosition`.
- На КП вибрані кроки можна перенести в новий активний проєкт. Користувач задає назву; новий проєкт отримує новий ID і наступну позицію серед активних проєктів. Вибрані завдання зберігають ID, списки, секції, дати, статуси та інші власні поля; змінюються лише `projectId`, `projectPosition` (послідовно від нуля в попередньому відносному порядку) та `updatedAt`. Невибрані кроки залишаються у вихідному проєкті. Створення проєкту й перенесення всіх вибраних кроків виконуються однією транзакцією `projects` і `tasks`.
- У редакторі активного кроку можна перепризначити його до іншого активного проєкту. Завдання зберігає ID та власні поля; `projectId` змінюється на вибраний проєкт, `projectPosition` ставиться після його останнього кроку, `updatedAt` оновлюється. У вихідному проєкті проміжок позицій допустимий до ручного впорядкування.
- Новий проєкт отримує `position` на одиницю більшу за найбільшу позицію активних проєктів. Активні проєкти впорядковуються за `position`, потім за `createdAt` та `id`; завершення, видалення й відновлення не нормалізують позиції, а ручна перестановка перепризначає їх послідовно.
- Активне завдання без `projectId` можна перетворити на новий активний проєкт. Збережені кроки, якщо вони є, відновлюються як нові завдання в порядку масиву. Відсутній список замінюється на «Нові», а відсутня чи перенесена секція — на корінь списку. Беруться поточні значення редактора; спільне правило переносить лише `title`, `description`, `dueDate` і `dueTime`. Проєкт отримує новий ID і наступну позицію серед активних проєктів; решта його полів мають звичайні значення за замовчуванням. `customFields` завдання не копіюються, бо їхній вміст може мати значення лише для завдань. Створення проєкту й кроків та видалення вихідного завдання відбуваються в одній транзакції `projects`, `tasks`, `lists` і `sections`; за помилки завдання залишається.
- Активний крок наявного проєкту можна зробити самостійним. Поточні значення редактора записуються разом із перенесенням того самого завдання до кореня його поточного списку: `listId` зберігається, `sectionId`, `projectId` і `projectPosition` стають `null`, `position` стає `0`, `updatedAt` оновлюється. Решта власних даних завдання, зокрема ID і `createdAt`, зберігаються. Позиції інших завдань у корені цього списку зсуваються на одиницю в тій самій транзакції. Проміжок у `projectPosition` решти кроків допустимий до наступної ручної перестановки.
- Для активного кроку наявного проєкту модалка дає вибір: зробити його самостійним завданням у поточному списку або перетворити безпосередньо на новий проєкт. У другому випадку спільне правило копіює `title`, `description`, `dueDate` і `dueTime` з поточного редактора до нового активного проєкту без кроків. Створення проєкту й видалення вибраного кроку відбуваються однією транзакцією `projects` і `tasks`; вихідний проєкт та решта кроків не змінюються. Їхній відносний порядок зберігається, а наступний активний крок обчислюється за наявним правилом. Після обох варіантів тост на 3 секунди дозволяє скасувати дію; скасування також записується атомарно.
- Активний проєкт можна перетворити на нове активне завдання в корені «Нові». Новий запис отримує власний ID, `title`, `description`, `dueDate` і `dueTime` з поточного редактора проєкту; `goal`, `customFields` та інші поля проєкту не копіюються. Типово активні невиконані кроки потрапляють до `savedSteps`, а всі вихідні кроки видаляються. Також можна залишити кроки окремими завданнями або видалити їх. Позиції завдань у корені «Нові» зсуваються для нового завдання. Створення завдання, зміни чи видалення кроків і видалення проєкту виконуються однією транзакцією `projects` і `tasks`.
- Порядок завдань у звичайному списку визначає `position` у межах пари `listId + sectionId`; однакові або відсутні позиції стабільно розв'язуються за `createdAt` (новіші вище), а потім за `id`.
- На екранах «Сьогодні» і «Завтра» завдання з різних списків мають спільний незалежний порядок у плані відповідної дати. Нові для плану завдання показуються першими за спаданням `createdAt`; порядок вихідних списків не змінюється. Після зміни доби план учорашнього «Завтра» стає планом «Сьогодні», бо ключем є дата.
- Після ручної перестановки позиції всіх завдань у відповідній області нормалізуються до `0, 1, 2…`; порядок кроків проєкту незалежно визначає `projectPosition`.
- У режимі виділення завдання можна перетягувати всередині секції, між секціями та між секцією й коренем того самого списку. Переміщення змінює `sectionId` і нормалізує `position` у всіх зачеплених областях; `listId` і порядок кроків проєкту залишаються без змін.
- Системний Інбокс завжди відображається першим. Після ручної перестановки одного або групи вибраних користувацьких списків їхній взаємний порядок зберігається, усі `position` нормалізуються до `0, 1, 2…` і записуються однією транзакцією.
- Звичайний список показує активні завдання без проєкту та лише поточний крок кожного проєкту.
- Переміщення завдання до іншого списку скидає несумісний `sectionId` у `null`.
- Видалення секції не видаляє завдання; їхній `sectionId` стає `null`.
- Під час видалення одного або кількох проєктів користувач обирає: залишити пов'язані завдання (тоді їхні `projectId` і `projectPosition` стають `null`) або видалити їх разом із проєктом. Проєкти й пов'язані завдання змінюються однією транзакцією.
- Під час завершення одного або кількох проєктів користувач обирає: завершити їхні активні завдання або залишити завдання активними у відповідних списках без проєкту. Завершення проєктів і зміни активних завдань виконуються однією транзакцією; вже завершені завдання залишаються історією проєкту.
- Видалення звичайного списку переміщує його завдання до Інбоксу.

## Розширення моделі

Новий атрибут спочатку додається до фабрики відповідної сутності в `src/js/model.js` із безпечним значенням за замовчуванням. Існуючі записи мають читатися толерантно до відсутнього поля. Якщо для поля не потрібен IndexedDB-індекс, версію бази змінювати не треба. Якщо потрібні новий store, індекс або структурна міграція — збільшується `DB_VERSION` і додається збережувальний upgrade-крок у `src/js/db.js`.

`customFields` призначене для атрибутів, які ще не стали частиною стабільного домену. Важливі поля, за якими фільтрують, сортують або будують бізнес-правила, мають бути явними полями сутності.

## Резервна копія

Злиття зі старою резервною копією після перетворення може повернути видалене вихідне завдання або крок проєкту: поточний формат копій не поширює видалення. Новий проєкт при цьому зберігається як окремий запис.

Формат 20 експортує доменні stores і `settings`, включно зі станом згортання секцій, усіма денними планами та налаштуванням `calendar-range` (`month`, `3-weeks`, `2-weeks`, `1-week`), одним узгодженим знімком з read-only транзакції. За відсутності цього налаштування використовується `month`; версія IndexedDB не змінюється. Envelope має `format`, `appId`, `formatVersion`, `databaseVersion` (довідково), `exportedAt` і `data` з масивами `lists`, `sections`, `projects`, `tasks`, `settings`. Імпорт форматів 1–19 підтримується: відсутні поля старих записів отримують безпечні значення, відсутній системний Інбокс відтворюється, а `today-layout` переноситься до плану записаної в ньому дати. Структура кожного плану перевіряється до запису; посилання на невидимі задачі прибираються нормалізацією. Під час злиття записи однакової дати зіставляються за `updatedAt` (за рівності залишається локальний), а плани різних дат зберігаються окремо.

У НаГ користувач завантажує JSON або вибирає файл для відновлення. Перед записом застосунок перевіряє структуру, унікальність ID, типи полів і зв’язки; показує дату й кількість записів. Заміна повністю відтворює файл. Злиття додає відсутні ID, а при однаковому ID бере запис із пізнішим `updatedAt`; за рівності часу залишає локальний. Видалення не поширюються злиттям, бо історія видалень не зберігається. Після злиття зв’язки перевіряються повторно; несумісний результат відхиляється. Обидва режими записують усі stores в одній транзакції, тому збій не залишає частково відновлених даних. Натискання «Злити дані» або «Замінити всі дані» одразу запускає імпорт. Попередній стан зберігається в пам’яті; протягом 3 секунд toast пропонує відмінити імпорт і відновити цей стан однією транзакцією. Файли понад 50 МБ відхиляються з повідомленням; кількість записів не обмежується окремо.

Для швидкого імпорту у браузерах із File System Access API користувач один раз вибирає папку бекапів. Її `FileSystemDirectoryHandle` зберігається лише локально в окремій базі `dims-tasks-local-files` (store `handles`, ключ `backup-directory`), не експортується в JSON і не переноситься на інші пристрої. Прапорець «Найновіший бекап» увімкнений за замовчуванням: програма перевіряє JSON-файли в обраній папці, ігнорує сторонні або пошкоджені та відкриває попередній перегляд найновішої придатної копії за `exportedAt` (або часом зміни файлу, якщо дати експорту немає). Коли прапорець вимкнений, програма показує перелік JSON-файлів із цієї папки для ручного вибору. Якщо API недоступний, лишається звичайний системний вибір окремого JSON-файлу. Доступ до папки може потребувати повторного дозволу браузера; сам імпорт завжди вимагає окремого вибору злиття або заміни.

Якщо папку вже вибрано і браузер дозволяє запис, «Експорт бекапу» створює JSON безпосередньо в цій папці. Дозвіл на запис може запитуватися окремо від дозволу на читання. Ім'я та вміст мають той самий формат, що й звичайне завантаження. Якщо ім'я зайняте, додається суфікс ` (2)`, ` (3)` тощо без перезапису наявного файлу. Лічильник наступної копії збільшується лише після успішного закриття записаного файлу. Без вибраної папки або без підтримки API експорт, як і раніше, завантажує JSON через браузер.
